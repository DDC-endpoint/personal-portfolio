## Finding 1: the blank portrait on Android (root cause found, fix on the branch)

**Symptom:** on every Android phone Damian tried (Chrome, Brave, and the Claude app's in-app browser), the portrait stage stays empty forever and the `Portrait · N × M cells` label never appears. iPhone Safari works. Chromium's phone emulation on Windows works, which is why the tests never caught it.

**Cause:** `HeroPortrait.jsx` waits on `document.fonts.load(\`700 6px ${family}\`)`, where `family` is next/font's list `"JetBrains Mono", "JetBrains Mono Fallback"`. next/font's fallback face is `@font-face { font-family: JetBrains Mono Fallback; src: local(Arial); … }` (checked in the built CSS). **Android has no Arial**, so that face fails to load, and `document.fonts.load()` then **rejects with `NetworkError`** for the whole list (reproduced in Chromium with a face pointing at a missing local font: `REJECTED NetworkError: A network error occurred.`). The portrait's `Promise.all` lands in `.catch`, which sets `data-state="error"`: a blank stage with no label. Windows has Arial, so desktop and emulation never fail.

**How it was narrowed down:**
1. Live site under Chromium's Pixel 7 emulation: the portrait reaches `static` (98 × 80 cells) and draws. So it's not the code path in general.
2. A private test page (claude.ai artifact `https://claude.ai/artifact/UcS8iQDvCfHUVvPCCxCDFU`, source in `perf-probes/portrait-check.template.html`; the portrait's base64 replaces `__B64__`) that runs each pipeline step. On Damian's Android phone (Chrome 156, Android 10, DPR 2.34, 461×847): **every step passed**, including `createImageBitmap` with resize, pixel readback and drawing, but its font step loaded `"JetBrains Mono"` alone. That pointed at the one difference: the fallback family in the site's list.
3. The `NetworkError` reproduction above.

**Fix (on the branch):** `const font = document.fonts.load(…).catch(() => [])`. A face that can't load no longer stops the portrait; the canvas falls back down the family list by itself, so the drawing is unchanged wherever the real font loads.
**Test:** `e2e/portrait.spec.js` → "a fallback font face that can't load still draws the portrait" (adds a `"JetBrains Mono Fallback"` 700 face with `src: local("No Such Font Anywhere")`). It failed before the fix and passes after.
**Not yet done:** confirm on a real Android phone after a deploy (the stage draws and the label shows). Also check whether anything else waits on `document.fonts.load` with the full family list (`MorphLoader` uses `document.fonts.ready`, which doesn't reject).

## Finding 2: the curtain's moving shadow (fix on the branch)

**Measured** (local production build, real GPU, `perf-probes/perf.mjs`, a visible window at 1536×864 @ 1.25):

| | page change → `/services` | page change → Home |
|---|---|---|
| live site, as is | ~48-52 fps, 16-22 frames over 25 ms | ~48-52 fps, ~40-50 over 25 ms |
| live, curtain `[data-drop]{filter:none}` | 59 fps, 1 over 25 ms | ~52 fps, ~44 |
| live, a constant resting drop-shadow only | 58 fps, 2 | 56 fps, 30 |
| live, `[data-shape]{clip-path:none}` as well | no further gain | no further gain |
| live, `.grain` hidden | no gain | no gain |

**Cause:** each frame, `components/transition/curtain.js` rewrote `filter: drop-shadow(…) drop-shadow(…)` on all five panels (130vh tall) with a new blur radius, offset and alpha, so the GPU re-blurred every panel every frame. A constant filter is cheap even though the clip-path changes every frame.

**Fix (on the branch), the same look:**
- The resting shadow is one constant filter (`lib/curtain.js` → `restFilter`), written only when it changes (a theme switch).
- The moving shadow is a blurred copy of the panel's shape behind it (`Curtain.jsx` → `data-trail` / `data-trail-shape`, filled `bg-ink`, `dark:bg-black`). Per frame the engine changes its offset and opacity (`lib/curtain.js` → `trail`) and its clip-path. Its `blur()` is the drop-shadow's own blur radius divided by two (a drop-shadow's radius `b` is a Gaussian of deviation `b / 2`, which is what `blur()` takes), rounded to whole px, so it changes a few times a move instead of every frame. Opacity, offset, colour and shape are the same numbers `shadow()` gave the drop-shadow, and below the old 0.004 alpha threshold it's off, as before.
- `shadow()`'s numbers are untouched. Unit tests: `tests/unit/curtain.test.js` (196 unit tests pass).

**Measured after** (first version, with the trail blur fixed at 9 px; headless new-mode Chromium on the GPU, which shows the effect more faintly than a window): `/services` 1-6 frames over 25 ms against 2 for the no-shadow floor. **The final version (blur matched to the speed) has not been re-measured,** and the look has **not yet been compared frame by frame** with the live site. Do both before merging: screenshot the same moments of a page change (for example hold the curtain mid-lift) on `main` and on the branch, light and dark, and diff them.

## Finding 3: the portrait canvas is the main cost of the first load and of arriving on Home

**Measured** (local production build, headless on the GPU): the first load runs at about 35-40 fps (83-90 frames over 25 ms in its first ~5.8 s), and a page change to Home at 45-50 fps, even with the curtain's shadows off. Isolation by CSS:

| override | first load | change → Home |
|---|---|---|
| none | ~35-40 fps, 83-90 | ~45-50 fps, 46-56 |
| `[data-portrait]{display:none}` (its loop pauses off screen) | **56 fps, 5** | **60 fps, 1** |
| `.blob{display:none}` (the hero's blurred orbs) | 44 fps, 70 | 50 fps, 44 |
| `.morph-loader [data-orb]{display:none}` | 41 fps, 69 | 48 fps, 53 |

So the portrait's per-frame drawing is the cost; the orbs and the loader barely matter. Long-animation-frame entries show the portrait's rAF callback at 8-19 ms of script per frame, plus GPU work.

**Change 1 (on the branch, not yet measured):** before its wave starts (the whole time the curtain covers it, loader included) the portrait redrew its full skeleton every frame, although time is held at −1 then, so every frame was the identical picture. It now draws that still once (`stillDrawn` in `HeroPortrait.jsx`) and again only after a new rest canvas (a resize or a theme switch). The lens waits for the reveal anyway, so nothing else needs drawing then. No visual change.

**Change 2 (planned, not started):** batch `drawWave`. Per frame it makes about three canvas calls for every cell the wave hasn't reached (thousands on desktop): `clearRect`, then a skeleton `fillRect` with its own `globalAlpha`, or a noise `fillText`. Plan:
- clear every unrevealed cell with one path (`destination-out`), not one `clearRect` each;
- group the skeleton blocks by opacity, rounded to the canvas's 8-bit precision, into a few dozen `fill()`s (the blocks never overlap, so the coverage is identical);
- leave the noise glyphs as `fillText` (they're random per frame anyway).
Prove it before shipping with a pixel diff of the old against the new `drawWave` at fixed `t` (stub `Math.random`), and keep the idle loop as it is unless a measurement says otherwise. The idle scan band (about 1,500 `fillText` a frame for 2.4 s of every 6 s) is a later candidate.

## Finding 4: slow connections and the loader (analysed, nothing changed yet)

A phone-emulated load of the live site from this laptop (`perf-probes/reqs.mjs`): HTML 3.3 s, the 13 JS chunks done at about 10 s, `load` at 10.2 s. **The portrait (`/hero/portrait.webp`, 47 KB) is only requested after hydration** (10.3 s in), because `HeroPortrait` fetches it from an effect. The curtain's engine is a separate chunk imported at hydration, another round trip. Meanwhile the CSS failsafe dissolves the intro curtain at 5 s, and a hydration after that skips the intro (by design), so on a slow link the page shows with an empty portrait stage for seconds.

Candidates, none built yet (all invisible on a fast connection):
- `<link rel="preload" href="/hero/portrait.webp" as="fetch" crossorigin>` on Home, so the fetch starts with the HTML (it must match `fetch()`'s mode for the preload to be used).
- Preload or prefetch the curtain engine's chunk.
- `/hero/portrait.webp` is served with `Cache-Control: public, max-age=0`, so a return visit revalidates it. Give `/hero/*` a long cache (it would then need a versioned name when the image changes).
- Check whether nginx serves HTTP/2. This laptop's curl lacks HTTP/2, so it showed `HTTP/1.1`, which proves nothing. Verify with a browser's Network panel (Protocol column) or `curl --http2` elsewhere. If it's HTTP/1.1, enabling `http2` in nginx is the biggest single win for the 13 chunks on a high-latency link (server-side, outside this repo).

## The probes (`docs/v3/perf-probes/`)

Run from the repo root so `@playwright/test` resolves; they need `npx playwright install chromium`.
- `perf.mjs <base-url> [cpuThrottle] [headed]`: frame times (rAF intervals) and long-animation-frame entries through the first load, the idle hero, a change to `/services` and back to Home. `CSS="<rules>"` injects CSS overrides (how every isolation above was done). It launches `channel: "chromium"` with `--enable-gpu --ignore-gpu-blocklist --use-angle=d3d11`. The `headed` mode opens a visible window on the user's screen: warn first or avoid it (it surprised Damian). New-headless shows the same effects, more faintly.
- `reqs.mjs`: a phone-emulated load of the live site with every request's start and duration, and the portrait's state after 25 s.
- `fontcheck.mjs`: the `document.fonts.load` rejection with a missing local font.
- `phone-diag.js`: paste into a phone's DevTools console (via `edge://inspect` or `chrome://inspect` with USB debugging) on damiandc.com; prints each portrait pipeline step. Its font step loads only `"JetBrains Mono"`; use the site's full family list to see the Android failure.
- `portrait-check.template.html`: the phone test page, published as a private artifact (above).
