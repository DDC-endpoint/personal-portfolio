## Finding 1: the blank portrait on Android (root cause found, fix on the branch)

**Symptom:** on every Android phone Damian tried (Chrome, Brave, and the Claude app's in-app browser), the portrait stage stays empty forever and the `Portrait · N × M cells` label never appears. iPhone Safari works. Chromium's phone emulation on Windows works, which is why the tests never caught it.

**Cause:** `HeroPortrait.jsx` waits on `document.fonts.load(\`700 6px ${family}\`)`, where `family` is next/font's list `"JetBrains Mono", "JetBrains Mono Fallback"`. next/font's fallback face is `@font-face { font-family: JetBrains Mono Fallback; src: local(Arial); … }` (checked in the built CSS). **Android has no Arial**, so that face fails to load, and `document.fonts.load()` then **rejects with `NetworkError`** for the whole list (reproduced in Chromium with a face pointing at a missing local font: `REJECTED NetworkError: A network error occurred.`). The portrait's `Promise.all` lands in `.catch`, which sets `data-state="error"`: a blank stage with no label. Windows has Arial, so desktop and emulation never fail.

**How it was narrowed down:**
1. Live site under Chromium's Pixel 7 emulation: the portrait reaches `static` (98 × 80 cells) and draws. So it's not the code path in general.
2. A private test page (claude.ai artifact `https://claude.ai/artifact/UcS8iQDvCfHUVvPCCxCDFU`, source in `perf-probes/portrait-check.template.html`; the portrait's base64 replaces `__B64__`) that runs each pipeline step. On Damian's Android phone (Chrome 156, Android 10, DPR 2.34, 461×847): **every step passed**, including `createImageBitmap` with resize, pixel readback and drawing, but its font step loaded `"JetBrains Mono"` alone. That pointed at the one difference: the fallback family in the site's list.
3. The `NetworkError` reproduction above.

**Fix (on the branch):** `const font = document.fonts.load(…).catch(() => [])`. A face that can't load no longer stops the portrait; the canvas falls back down the family list by itself, so the drawing is unchanged wherever the real font loads.
**Test:** `e2e/portrait.spec.js` → "a fallback font face that can't load still draws the portrait" (adds a `"JetBrains Mono Fallback"` 700 face with `src: local("No Such Font Anywhere")`). It failed before the fix and passes after.
**Not yet done:** confirm on a real Android phone after a deploy (the stage draws and the label shows). Also check whether anything else waits on `document.fonts.load` with the full family list (`MorphLoader` uses `document.fonts.ready`, which doesn't reject).

## Finding 2: the curtain's moving shadow (fix on the branch)

**Measured** (local production build, real GPU, `perf-probes/perf.mjs`, a visible window at 1536×864 @ 1.25):

| | page change → `/services` | page change → Home |
|---|---|---|
| live site, as is | ~48-52 fps, 16-22 frames over 25 ms | ~48-52 fps, ~40-50 over 25 ms |
| live, curtain `[data-drop]{filter:none}` | 59 fps, 1 over 25 ms | ~52 fps, ~44 |
| live, a constant resting drop-shadow only | 58 fps, 2 | 56 fps, 30 |
| live, `[data-shape]{clip-path:none}` as well | no further gain | no further gain |
| live, `.grain` hidden | no gain | no gain |

**Cause:** each frame, `components/transition/curtain.js` rewrote `filter: drop-shadow(…) drop-shadow(…)` on all five panels (130vh tall) with a new blur radius, offset and alpha, so the GPU re-blurred every panel every frame. A constant filter is cheap even though the clip-path changes every frame.

**Fix (on the branch), the same look:**
- The resting shadow is one constant filter (`lib/curtain.js` → `restFilter`), written only when it changes (a theme switch).
- The moving shadow is a blurred copy of the panel's shape behind it (`Curtain.jsx` → `data-trail` / `data-trail-shape`, filled `bg-ink`, `dark:bg-black`). Per frame the engine changes its offset and opacity (`lib/curtain.js` → `trail`) and its clip-path. Its `blur()` is the drop-shadow's own blur radius divided by two (a drop-shadow's radius `b` is a Gaussian of deviation `b / 2`, which is what `blur()` takes), rounded to whole px, so it changes a few times a move instead of every frame. Opacity, offset, colour and shape are the same numbers `shadow()` gave the drop-shadow, and below the old 0.004 alpha threshold it's off, as before.
- `shadow()`'s numbers are untouched. Unit tests: `tests/unit/curtain.test.js` (196 unit tests pass).

**Measured after** (first version, with the trail blur fixed at 9 px; headless new-mode Chromium on the GPU, which shows the effect more faintly than a window): `/services` 1-6 frames over 25 ms against 2 for the no-shadow floor. **The final version (blur matched to the speed) has not been re-measured,** and the look has **not yet been compared frame by frame** with the live site. Do both before merging: screenshot the same moments of a page change (for example hold the curtain mid-lift) on `main` and on the branch, light and dark, and diff them.

**Measured** (local production build, headless on the GPU): the first load runs at about 35-40 fps (83-90 frames over 25 ms in its first ~5.8 s), and a page change to Home at 45-50 fps, even with the curtain's shadows off. Isolation by CSS:

|---|---|---|
| none | ~35-40 fps, 83-90 | ~45-50 fps, 46-56 |
| `[data-portrait]{display:none}` (its loop pauses off screen) | **56 fps, 5** | **60 fps, 1** |

| `.morph-loader [data-orb]{display:none}` | 41 fps, 69 | 48 fps, 53 |

So the portrait's per-frame drawing is the cost; the orbs and the loader barely matter. Long-animation-frame entries show the portrait's rAF callback at 8-19 ms of script per frame, plus GPU work.

**Change 1 (on the branch, not yet measured):** before its wave starts (the whole time the curtain covers it, loader included) the portrait redrew its full skeleton every frame, although time is held at −1 then, so every frame was the identical picture. It now draws that still once (`stillDrawn` in `HeroPortrait.jsx`) and again only after a new rest canvas (a resize or a theme switch). The lens waits for the reveal anyway, so nothing else needs drawing then. No visual change.

**Change 2 (planned, not started):** batch `drawWave`. Per frame it makes about three canvas calls for every cell the wave hasn't reached (thousands on desktop): `clearRect`, then a skeleton `fillRect` with its own `globalAlpha`, or a noise `fillText`. Plan:
- clear every unrevealed cell with one path (`destination-out`), not one `clearRect` each;
- group the skeleton blocks by opacity, rounded to the canvas's 8-bit precision, into a few dozen `fill()`s (the blocks never overlap, so the coverage is identical);
- leave the noise glyphs as `fillText` (they're random per frame anyway).
Prove it before shipping with a pixel diff of the old against the new `drawWave` at fixed `t` (stub `Math.random`), and keep the idle loop as it is unless a measurement says otherwise. The idle scan band (about 1,500 `fillText` a frame for 2.4 s of every 6 s) is a later candidate.

### `drawWave` batching cannot be pixel-identical (gate question)

`perf-probes/wave-harness.mjs` draws the wave at fixed `t` with the old and a batched `drawWave` in the real page (same fonts, same accelerated canvas, `Math.random` stubbed) and diffs the pixels. Findings:
- On a GPU-accelerated 2D canvas **`clearRect` is antialiased**: a fractional edge clears a pixel partially, so two adjacent per-cell clears leave `c(1-c)` of the old alpha at their seam (up to a quarter). A tiny canvas (the CPU path) is not antialiased, so a small probe misleads. One path over all unrevealed cells clears the seams fully; snapping it to whole device pixels (even with Skia's float32 rounding) still differs, since the old clears were partial at the edges.
- Drawing every cell after clearing them all changes the overflow: a noise glyph's descender spills into the row below and its right edge into the next cell, which the old per-cell clear erased when it reached that cell. Clearing row by row keeps the descender rule but not the right-edge one.
- Cost on this machine (per wave frame, median of 30): old 18-21 ms at `t = 0.8` (12-13 ms at the still, all-skeleton frame); one path per row then the cells, 7-10 ms (6-7 ms). The breakdown at `t = 0.8`: the 8,770 clears 5 ms, the skeleton rects 2.5 ms, the 1,800 noise glyphs 4 ms; interleaving the clears with the draws costs the rest (each `clearRect` breaks the GPU batch).
- The differences of the best variant (one `destination-out` path per row, then that row's cells): at `t ≤ 1.4` 1-2% of the canvas's pixels, mostly by 1-4/255 at cell seams (the old seam residue) and up to 255 on a few pixels where a glyph's right edge spilled into the next cell; none at `t ≥ 1.6`. Invisible side by side, not identical. **Decision for Damian:** build it (about half the wave's script time; the wave is the first load's heaviest 2.4 s) or leave the wave as it is.

  **The structural fix, built and measured (Damian's go-ahead):** `components/transition/curtain.js` now works out each move in advance (`lib/curtain.js` → `sampleMove`, a 120 Hz grid, the same eased travel and shadow maths) and hands the panels' transforms to the Web Animations API, with a rAF loop writing the edges, the trail and the edge light from the same frames (`0e49ccc` and the hybrid that followed). Two things came out of measuring it on the phone with presented frames (`perf-probes/phone-trace.mjs`: a Chrome trace's `Display::FrameDisplayed` events, the display's own record, which keeps counting while the renderer's main thread is stalled; rAF counts can't see the compositor's work):
  - **Keyframing everything was worse** (57-73 frames shown over the change against 83-87 for the per-frame engine, with 100-250 ms gaps): an animated element gets a compositor layer of its own, and the trail's is a panel-sized blurred one, re-blurred by the GPU every frame; a keyframed `clip-path` costs a mask a frame. With only the panels' transforms on the compositor the hybrid is at **parity** (91-96 frames against 90, no gap over 100 ms), not better.
  - **The stall is the curtain's own raster, not the main thread.** CSS overrides on the phone, presented frames over the 2.2 s change: as is 82 (37 fps, 12 gaps over 50 ms); without the trail 92 (8); without the clip-path 89 (10); without both 102 (4); without both and the resting `drop-shadow` on `[data-drop]` **131 (59 fps, 1 gap)**. The panel's layer repaints every frame (its bulge, trail and edge light change), and each repaint re-rasterises the 14 px drop-shadow of a 130vh panel, five times over, on a Mali GPU at 2.75×. The per-frame engine had the same cost, which is why the engines tie.
  - On the desktop (240 Hz, RTX 4060) the display presents every vsync whatever changes, so `desktop-trace.mjs` can't tell the engines apart there; the hybrid's benefit (panels moving through a main-thread stall) stays a property of the design, measured nowhere yet.

  **What would make the phone lag-free (for Damian):** separate what changes per frame from what is static, so the expensive raster happens once. The panel body as a plain rect with its resting shadow, rasterised once and moved by the compositor; the curved caps (top and bottom, about 9vh tall) as small elements of their own that carry their own shadow and repaint per frame cheaply; the trail as pre-blurred content (an SVG blur rasterised once, no live filter) that the compositor moves and fades, with small per-frame caps of its own. The geometry, colours and blur numbers stay; where a cap's shadow meets the body's, two overlapping shadows add to at most 1/255 less than one (9/255 in dark mode, where the resting shadow is 0.38), the only difference. A few hours with the frame-matched diff and `phone-trace.mjs` behind it.

  **The hybrid against the per-frame engine, frame-matched** (`perf-probes/curtain-diff2.mjs`, which drives the Web Animations by hand under the fake clock, moments on the clock's own 16 ms grid): 7-8% of pixels differ by up to 200 at the fastest moments of the cover, 0.02% by 1 during the hold. The 3× crops show the hybrid's panel a few px further along at the same moment: the engines' clocks start a frame apart (the old one's first step lands on the next rAF), not a different curve.

  **The structural fix (for Damian), the earlier note:** drive the panels from the compositor instead of a rAF loop: precompute each move's keyframes (transform, clip-path, edge-light and trail opacity, the trail's offset) from the same maths at a fine step and play them with the Web Animations API, so a 150 ms main-thread stall can't freeze them (transform and opacity run on the compositor; whether Chrome composites a `path()` clip-path animation must be checked on the phone first, or the bulge alone would pause). Visually it's the same curve sampled on a fixed grid rather than on whatever frames the device managed, which on a laggy device is closer to the design, not further. It replaces the engine's per-frame `draw()` (`components/transition/curtain.js`), about a day with the frame-matched diff and the phone measurements. The other half is the mount cost of `/services` itself (profile its first layout and paint; `content-visibility` on below-the-fold sections is the usual lever, but it interacts with the pinned Timeline and the scroll-driven effects, so it needs the e2e suite behind it).

## The probes (`docs/v3/perf-probes/`)

Run from the repo root so `@playwright/test` resolves; they need `npx playwright install chromium`.
- `perf.mjs <base-url> [cpuThrottle] [headed]`: frame times (rAF intervals) and long-animation-frame entries through the first load, the idle hero, a change to `/services` and back to Home. `CSS="<rules>"` injects CSS overrides (how every isolation above was done). It launches `channel: "chromium"` with `--enable-gpu --ignore-gpu-blocklist --use-angle=d3d11`. The `headed` mode opens a visible window on the user's screen: warn first or avoid it (it surprised Damian). New-headless shows the same effects, more faintly.
- `reqs.mjs`: a phone-emulated load of the live site with every request's start and duration, and the portrait's state after 25 s.
- `fontcheck.mjs`: the `document.fonts.load` rejection with a missing local font.
- `phone-diag.js`: paste into a phone's DevTools console (via `edge://inspect` or `chrome://inspect` with USB debugging) on damiandc.com; prints each portrait pipeline step. Its font step loads only `"JetBrains Mono"`; use the site's full family list to see the Android failure.
- `portrait-check.template.html`: the phone test page, published as a private artifact (above).
- `slowlink.mjs <base-url> [downKbps] [rttMs] [cpu]`: a phone-emulated first load over a throttled link: every request's start and end, and when the curtain, the portrait and the transitions change state.
- `preload-probe.mjs [base-url]`: the portrait's resource entries (initiator and bytes) on desktop and phone sizes, to see whether the preload is used.
- `curtain-diff.mjs <urlA> <urlB> <outdir>`: frame-matched screenshots of a page change on two builds under a fake clock, light and dark, and the pixel diff of each pair. `diffimg.mjs a b out` makes an amplified diff image; `crop.mjs a b out x y w h` a side-by-side 3× crop.
- `wave-harness.mjs [base-url]`: the portrait's `drawWave`, old against batched, at fixed `t` with `Math.random` stubbed: pixel diffs and per-frame timings. The batched variant in it is the row-by-row one.
- `phone.mjs`, `phone-perf.mjs`, `phone-profile.mjs`, `phone-touch.mjs`: the USB phone over CDP (see "Damian's phone"): states and the clip-path at full cover; rAF frame times; a CPU profile of a page change; real touch gestures on the portrait.
- `phone-trace.mjs <base-url>` (`CSS="…"` injects overrides): presented frames during a page change from a Chrome trace (`Display::FrameDisplayed`), the measure that sees the compositor's work. `phone-frames.mjs` tried the screencast for the same and can't (its frames need the main thread). `desktop-trace.mjs` is the same on this machine, where the display presents every vsync, so it tells nothing.
- `curtain-diff2.mjs`: `curtain-diff.mjs` for an engine on the Web Animations API, which the fake clock doesn't drive: it stamps each animation and sets its time by hand at each moment.
- `lh.sh label:url label:url …`: interleaved Lighthouse runs (mobile ×5, desktop ×3, `/`, `/services`, `/portfolio`) and a median table; `LH_OUT` sets the JSON folder.
